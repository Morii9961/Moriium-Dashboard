# 0002 · 协议包：预编译校验器、接收流水线与问题条目

- 日期：2026-10-12
- 状态：采用
- 范围：`packages/protocol`（P1.3）

## 背景

规划 05 第 4 节选了 JSON Schema 2020-12 + Ajv，要求前端预览和服务端复核用同一套代码（04 第 3 节）。同时，界面要有严格 CSP（启动提示词规则 4），导入时要能说清问题出在哪里、怎么改（04 第 7 节）。

## 决定

1. **Schema 正式版放在 `docs/protocol/schema/`**。从 `docs/planning/schema/` 复制过来，只改了顶层 `description`（去掉「草案」，指向正式文档）；字段、类型、枚举、约束逐项核对未变。规划目录里的草案保留原样，作为批准时的记录。

2. **校验器预编译**。Ajv 在运行时用 `new Function` 生成校验函数，严格 CSP（不允许 `unsafe-eval`）下浏览器会拒绝执行。改用 Ajv 的 standalone 模式，在开发时生成 `src/generated/validators.js`：
   - Ajv 即使在 ESM 模式下仍输出两处 `require()`（`ajv/dist/runtime/ucs2length` 和格式函数）。生成脚本把它们改写成从 `src/ajv-runtime.ts` 导入，所以生成结果是纯 ESM，运行时不依赖 ajv。ajv 只是开发依赖。
   - `date-time` 格式用我们自己的解析函数（同时用于计算 UTC 和原始偏移），不引入 ajv-formats。
   - 测试会比对「重新生成的结果」和仓库里的文件，Schema 或 Ajv 版本变了却忘记重新生成时测试失败。

3. **接收流水线**（`checkSnapshot`）：大小与编码 → 密钥扫描 → 解析（代码块先询问）→ 版本 → 规范化 → Schema 校验 → 语义校验 → 指纹。
   - **密钥扫描提前到解析之前**，和 04 第 3 节的顺序不同：解析失败时错误信息会引用出错位置附近约 40 个字符，先扫描能保证疑似密钥不会出现在任何输出里。合法文件的结果不受影响。
   - **先规范化，再用严格 Schema 校验**：去掉协议没有的字段（记提醒）、补上可以安全推断的默认值（记规范化）。这样 Schema 文件保持给生产者用的严格版本，宽松的部分集中在一处、逐条记录。`summary` 超过 160 字是唯一一个由 Schema 报出、再降为提醒的问题。
   - **未知次版本**（例如 1.4）按已知最新版本校验；未知枚举值换成 `unknown`，优先级没有 `unknown`，换成 `null`，界面显示「优先级未知」。
   - 解析后先检查嵌套深度（上限 32 层），后面的递归处理不会耗尽调用栈。
   - 结构错误和语义错误一次全部列出，不在第一个错误处停下。

4. **问题条目只带代码和参数**，文案在 `messages/zh-Hans.ts`。命令行工具和界面共用；日文、英文在 P2.2 补，不改代码。来自文件的文本（值、字段名、路径）在格式化时统一去掉控制字符和双向文本控制符，并截短。

5. **规则版本** `RULES_VERSION` 随快照入库。哪些算错误、哪些算提醒、怎么规范化，有实质变化时加一。

6. **语法错误自己定位**。`JSON.parse` 的报错在不同引擎里措辞不同，有的不带位置，还会引用文件内容。解析失败后用一个按 RFC 8259 写的小扫描器给出稳定的行列和原因。

7. **内容指纹**按 RFC 8785 规范化后取 SHA-256，用 Web Crypto 计算，浏览器和 Node 结果一致。原始字节另取 SHA-256。

## 后果

- 改 Schema（只允许发布新的次版本文件）或升级 Ajv 后，要运行 `pnpm --filter @moriium-dashboard/protocol generate`。
- 新增问题代码时，`messages/` 里要同时加文案；`formatIssue` 的 `switch` 由类型检查保证覆盖全部代码。
- 密钥形态在 `src/secrets.ts` 里维护一份，公开树审计也从这里导入。
