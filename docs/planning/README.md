## 执行摘要

**这是什么。** Moriium Dashboard 是 Morii 一个人用的工作台，与 Morii OS 无关。打开它，30 秒内要能知道四件事：今天先做哪一到三件事；哪个项目在等你决定或验收；哪些项目的报告过期了；最近做成了什么。它不是任务管理软件，也不是实时运维平台，目标是信息可信、看得快、维护省事。

**核心能力是「项目状态快照」。** 你在某个项目的 Agent 会话里说「生成项目状态快照」，Agent 按统一协议（Project Status Protocol v1）写出一份 JSON。你把文件拖进 Dashboard，它先校验、预览这份快照和上一份相比变了什么，你确认后才保存。重复的文件不会存两次；较旧的快照只进历史，不覆盖当前状态；格式有错时，Dashboard 用人话说明哪里错、怎么改，还能一键生成「给 Agent 的修复说明」。整个过程由你触发，不要求每天做，也不依赖 Agent 在线。

**「完成」分三种，永不混在一起。** Agent 自报完成、有仓库或测试证据、你亲自验收，在界面上始终分开显示。你在 Dashboard 里点的「验收通过」单独保存，比快照里的说法优先。快照没有给出可信的整体进度时，不画百分比进度条，改用阶段轴、里程碑和阻塞事项。所以主站和 Gallery 这类成熟项目会显示「功能成熟、等待上线」，不会因为没上线就显得完成度很低。

**调研结论。** 工作区里没有 Morii OS，也没有现成的任务系统；六个项目都还没有状态快照文件。能复用的是：各仓库已经在用的 `claude/`、`codex/` 分支前缀（可以判断报告来自哪个 Agent）、大量 handoff 文档（快照引用的依据）、Moriium 对「过期、未知、缺测」的处理方式和配色语义，以及它在同一台 VPS 上验证过的部署和登录做法。

**形态与技术。** 推荐做成浏览器访问的个人控制台：先在你自己的电脑上运行，用满一周、验收后再部署到 VPS。前端用 React + Vite + TypeScript，和 Enouia Runtime 的桌面端一致；另配一个很小的服务端，把数据存进一个 SQLite 文件，便于备份、多设备共用，也不让凭据进前端。代码公开在 GitHub，数据永远不进仓库。

**首版做什么。** 快照的导入、校验和历史对比；项目列表与详情；概览上的「需要你决定」；Agents 页显示「最后一次报告」；今日焦点、精力状态和基本任务；成果登记；自动备份和导出；中日英三语、浅深主题。GitHub 同步、自动读取报告、课程表、复盘等都放到以后，不阻塞首版。

**开发节奏。** 分七个阶段：P0 规划获批 → P1 仓库与协议 → P2 外壳与设计基线（与 P1 并行）→ P3 导入与历史 → P4 项目与概览 → P5 MVP 完成并试用一周 → P6 部署到 VPS。共约 31 个工作包，一个阶段大致一到两周。你只需要在七个节点参与，例如看一次设计样张、试导一轮真实文件、做一次 30 秒测试。

**Dashboard 自己的进度。** 它用同一套机制追踪自己。`docs/status/` 下已经建好初始快照：阶段为「规划中」，整体进度不估算，七个里程碑对应七个阶段，规划阶段不写任何「已实现」。

**需要你决定的五件事。** ① 是否采用「前端 + 本机小服务」；② 首版范围是否照此执行；③ 协议扩展 v1.1 先批准哪些；④ 仓库名、许可证，以及各项目的快照文件是否提交进各自的公开仓库；⑤ 部署后用私网还是公网访问（可以晚点定）。

**批准结果（2026-10-12）。** ① 前端 + 本机小服务（SQLite）；② 按 MVP 执行，各项目的进度展示列为首版重点（[02 第 5.4 节](./02-information-architecture-ux.md#54-进度展示的要求2026-10-12-morii-特别强调)）；③ 交给规划方决定：批准 E1、E2 组成协议 v1.1，E3、E4 暂缓；④ 同意；⑤ 回头再说，最晚 P6 前定。

## 规划阶段做了什么、没做什么

- 做了：只读查看了相关仓库的顶层结构、README、`package.json` 和状态、部署相关文档；写了本目录的规划文档和 `docs/status/` 下的初始快照。
- 没做：没有写功能代码，没有安装依赖，没有运行构建、测试或部署，没有建立 Git 仓库，没有修改其他项目的任何文件。

**规划已于 2026-10-12 获批，正式开发从 P1 开始。**
